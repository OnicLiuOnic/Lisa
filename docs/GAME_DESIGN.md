# 《老闆日報》遊戲設計文件

> 本文件已經過遊戲設計、數值平衡、技術架構、製作人四個專業角度的審查與修訂，文中標註「審查意見」處即為各角色提出並已採納的修改。全文採台灣繁體中文用語。

---

## 0. 文件摘要

一款**沒有任何美術資源**、純文字／報表驅動的經營模擬遊戲。玩家扮演一間商店的老闆，每天早上收到一份「晨報」，了解昨日經營結果與今日（依真實世界天氣／節假日資料模擬的）市場狀況，做出進貨、定價、員工、行銷四類決策後，商店依規則結算出今天的營業結果，產生新一天的晨報。如此日復一日，直到財務崩潰或達成經營目標。

---

## 1. 遊戲定位、目標受眾與單局時長

**一句話簡介**：一款用 Excel 般的報表取代美術、靠真實天氣與節日驅動劇情張力的單店經營模擬遊戲。

**目標受眾**：喜歡《大富翁》《主題醫院》一類經營模擬、但更偏好策略思考勝於操作反應的玩家；對「每天一回合」的輕度節奏（類似手機放置／策略遊戲的每日簽到感）有需求的玩家；不排斥純文字介面、重視數值邏輯與決策後果的核心玩家。

**單局時長**：
- 單一「天」的決策時間：1～3 分鐘（看報表、調整 2～4 項決策、送出）
- 單局完整遊玩（從開店到破產或達成目標）：建議落在 30～90 個遊戲日，real-time 約 1～3 小時可玩完一局，亦可分次遊玩（存讀檔）
- 此節奏設計目的：讓「每日決策」維持輕量、可在通勤／午休等零碎時間進行，但整體經營弧線仍有起承轉合

## 2. 核心循環（Game Loop）

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   晨報展示   │ --> │   玩家決策   │ --> │   當日結算   │ --┐
│ (Day N)     │     │ 進貨/定價    │     │ 計算銷售/   │   │
│             │     │ 員工/行銷    │     │ 現金流/事件 │   │
└─────────────┘     └─────────────┘     └─────────────┘   │
       ▲                                                    │
       └────────────────────────────────────────────────────┘
                         (Day N+1 晨報)
```

1. **晨報展示**：顯示昨日結算結果（營收、利潤、庫存、滿意度、流失訂單）、今日天氣／節假日資訊、一則新聞頭條、NPC 角色對昨日決策的評論。
2. **玩家決策**：在四個決策面板（進貨／定價／員工／行銷）中調整參數並送出。
3. **當日結算**：依第 4 節公式計算當日銷售與現金流，套用第 9 節防異常打法規則，必要時觸發隨機事件。

**隨機事件層（審查意見：遊戲設計師）**：若需求只由「天氣 × 節日 × 行銷」線性決定，玩家會在 3～5 天內摸透公式，進貨/定價變成單純填數字。因此每隔數天（機率觸發，非固定週期）插入一次**隨機事件**，事件本身不違反第 9 節的防套利規則，但會打破玩家對公式的直覺預期，例如：

| 事件 | 效果 | 觸發條件 |
|---|---|---|
| 競品促銷 | 鄰近商家當週同類商品降價，該品項今日 demand ×0.7 | 隨機，每 7～12 天機率觸發一次 |
| 食安／品質新聞衝擊 | 新聞頭條提及特定品類負面消息，該品類 demand ×0.5 持續 2～3 天 | 與當日新聞 flavor 文字綁定，見第 6 節 |
| 天氣預報失準 | 結算時的「模擬誤差」這天特別大（見第 6 節 AR(1) noise 在當天取較大絕對值） | 隨機，每 5～8 天機率觸發一次 |
| 進貨延遲 | 已下單商品延後 1 天到貨 | 隨機，機率與供應商評價掛勾（可作為擴充） |

## 3. MVP 決策維度（核心四件套）

### 3.1 進貨
- 從固定商品目錄（建議 MVP 6～10 個品項，分 2～3 個品類，如「民生用品」「天氣敏感品」「節慶禮品」）選擇品項與數量下單
- 前置時間（lead time）：1～3 天後到貨，依品項不同
- **倉儲／耗損成本（審查意見：數值平衡設計師）**：庫存超過「安全水位」（依商店規模設定，如 100 件）時，超出部分每日收取遞增倉儲費：
  `storage_cost = max(0, 庫存 − 安全水位) ^ 1.2 × 單位倉儲費率`
  指數 1.2 確保囤貨越多、邊際成本越高，避免「一次大量囤貨、之後躺著賣」的無腦最優解。

### 3.2 定價
- 每件商品可自由設定售價
- `ref_price`（參考價）**不是固定值**，而是「過去 14 天實際成交價的指數移動平均（EMA）」（審查意見：遊戲設計師＋數值平衡設計師）：
  `ref_price_t = α × cur_price_t + (1-α) × ref_price_(t-1)`，建議 `α ≈ 0.13`（對應 14 天半衰期）
  - 好處 1：防止「長期維持低價養大顧客基數、某天突然狂飆價格大撈一筆」的打法——因為長期低價會讓 `ref_price` 也跟著下降，狂飆價格時超出比例反而更大，被第 9 節機制重罰。
  - 好處 2：節慶前後市場價格自然會浮動，`ref_price` 跟著浮動，逼玩家持續關注定價而非設一次就不管。

### 3.3 員工
- 雇用／解雇、排班人數，決定每日可服務顧客上限（產能）與人事成本
- **最短任用期與資遣成本（審查意見：數值平衡設計師）**：雇用後至少維持 5 個遊戲日，提前解雇需支付資遣費（如 3 天薪資），防止「按天雇用臨時工、精準卡產能、零閒置成本」的打法
- **產能不足轉滿意度懲罰，而非單純流失訂單（審查意見：遊戲設計師）**：當日需求超過 `員工產能` 時，超額部分一半變成流失訂單，另一半變成「顧客排隊不耐」事件，直接扣減滿意度（見第 4 節），讓玩家必須在「多請人增加成本」與「讓顧客排隊傷口碑」之間做真實取捨，而非單純的產能填空題
- **加班超線性成本（審查意見：數值平衡設計師）**：若開放臨時加班提升當日產能，加班成本 `= 加班時數 ^ 1.5 × 時薪`，抑制「無限加班頂上去就好」的套利

### 3.4 行銷
- 每日可投入行銷預算，提升當日到店客流
- **事件型加成取代固定遞減曲線（審查意見：遊戲設計師）**：行銷效果不是「每天投入都打七折」的固定衰減，而是平時用凹函數計算基礎效果 `marketing_factor = 1 + k × log(1 + spend/baseline)`，但在「節慶前 1～2 天」「隨機事件期間」投放有**額外加乘**（如 ×1.5），逼玩家選擇時機而非每天定額投放
- 每日投放金額設上限，防止單日無限砸錢

## 4. 數值模擬公式

### 4.1 需求公式

```
demand = base_demand
       × price_factor
       × weather_factor
       × holiday_factor
       × marketing_factor
       × satisfaction_factor
       × noise
```

**總疊加倍率封頂（審查意見：數值平衡設計師）**：除了各別 factor 各自有上下限，`price_factor × weather_factor × holiday_factor × marketing_factor` 四者相乘的總倍率還要整體封頂在 `≤ 3.0`，避免多重利多疊加出超現實的單日暴衝（例如節慶 + 大雨 + 行銷三重加成同時觸發，理論上不該讓單日銷量是平常的 10 倍）。

#### price_factor（含防異常定價規則，見第 9 節）
```
若 cur_price ≤ 1.5 × ref_price：
    price_factor = (ref_price / cur_price) ^ elasticity
若 1.5 × ref_price < cur_price ≤ 2.5 × ref_price：
    超出比例 r = (cur_price / ref_price) − 1.5
    price_factor = (ref_price / (1.5×ref_price)) ^ elasticity × exp(-k × r)   // k 建議 3～5
若 cur_price > 2.5 × ref_price：
    price_factor = 0   // 硬性歸零，不依賴隨機數兜底
```

#### weather_factor / holiday_factor
依「商品品類 × 天氣類型 / 節假日」查表，範例：

| 商品品類 | 晴天 | 雨天 | 寒流 |
|---|---|---|---|
| 雨具 | 0.6 | 1.8 | 1.0 |
| 冰品飲料 | 1.3 | 0.7 | 0.4 |
| 民生用品 | 1.0 | 1.0 | 1.0 |

| 商品品類 | 平日 | 節慶前 1～3 天 | 節慶當天 |
|---|---|---|---|
| 節慶禮品 | 0.8 | 1.6 | 1.0（多數人已買完） |
| 民生用品 | 1.0 | 1.1 | 0.9（很多店休） |

#### satisfaction_factor
```
satisfaction_factor = 0.5 + (satisfaction / 100) × 1.0   // 範圍約 0.5 ~ 1.5
```

#### noise（防統計套利，審查意見：數值平衡設計師）
- 不採用獨立同分布的隨機數，改用 **AR(1) 時間相關噪聲**：`noise_t = ρ × noise_(t-1) + ε_t`（`ρ ≈ 0.4`，`ε_t` 為小幅常態分布）。獨立同分布的噪聲會讓玩家透過「同一價格連續試多天、統計平均成交率」反推出真實 demand 曲線；AR(1) 噪聲讓相鄰幾天的隨機性彼此相關，統計試探的訊噪比大幅下降。
- **UI 不顯示精確的 demand / 轉換率數字**給玩家，報表只呈現「實際成交量」與「定性的滿意度／口碑描述」，避免玩家用試算表反推公式係數。

#### 跨品項替代需求耦合（審查意見：數值平衡設計師）
若玩家把某品項定價壓到極低、其餘品項維持原價，部分原本會買其他相近品項（如同品類的競品）的需求會被「吸過來」，但總需求池有上限，避免「鎖定單一最低彈性品項、其他品項放著不管」的無腦最優解：
```
demand_i_adjusted = demand_i × (1 + 0.3 × Σ_j(同品類其他品項的相對提價幅度))
```

### 4.2 實際成交與滿意度

```
實際成交 = min(demand, 庫存量, 員工產能)
缺貨流失 = max(0, demand − 庫存量)      → 影響滿意度
產能流失 = max(0, demand − 庫存量 − 員工產能)，其中一半轉「排隊不耐」事件直接扣滿意度
```

### 4.3 現金流

```
現金流 = 營收 − 進貨成本 − 人事成本（含加班超線性成本） − 固定租金 − 行銷支出 − 倉儲超額費用 − （如觸發）銀行利息
```

## 5. 每日報表／UI 內容設計（「無美術」作為設計資產）

審查意見（製作人）指出：若只把「無美術」當成省成本的技術限制，文件就只是列了報表欄位，沒有真正用文字設計取代美術的情緒渲染。以下用具體範例說明如何讓純文字介面本身承擔「情緒節奏」的功能。

### 5.1 晨報頭條區
- 今日天氣預報（圖示用 emoji 或 ASCII 取代，如 `☀️ 晴 28°C` / `🌧️ 雨 19°C`）
- 是否節假日／距下個節假日剩幾天
- 一則新聞頭條（flavor text，見第 6 節）
- **固定 NPC 角色評論（審查意見：遊戲設計師）**：設定 2～3 個固定角色（如「常客陳太太」「隔壁競爭對手老王」「員工小美」），依昨日決策結果隨機抽選一句評論台詞，用文字情緒取代視覺回饋。範例：
  - 缺貨時：「陳太太：『我都跑三趟了還是沒貨，你們是不想做生意嗎？』」
  - 漲價過頭時：「老王：『隔壁那家又在亂喊價，這次客人全跑來我這了，謝謝啦！』」
  - 滿意度回升時：「小美：『今天客人心情都不錯，連早班都輕鬆很多。』」

### 5.2 經營儀表板
現金餘額、昨日營收／利潤、庫存明細表、顧客滿意度（以文字分級呈現如「極度不滿／普通／讚不絕口」而非裸數字，避免玩家精算反推公式）、流失訂單提示。

### 5.3 用排版與節奏表現壓力（具體範例）
- 現金餘額連續下滑時，數字旁加上漸強的警示符號密度（如餘額 < 安全水位的 50% 時顯示 `⚠️`，< 20% 時顯示 `⚠️⚠️⚠️` 並改變該行文字顏色／加粗），用「視覺密度」取代圖像
- 報表整體採「條列越短、行距越密」表現緊張的日子（如銀行已介入、隨機事件爆發當天），平日報表則排版寬鬆、語氣輕鬆，讓玩家透過排版疏密直覺感受「今天不太對勁」

### 5.4 音效角色（審查意見：製作人）
雖然沒有美術，仍建議搭配輕量音效作即時回饋，這在純文字遊戲中可大幅補足「真實感」：
- 成交：清脆的「收銀機」音效
- 缺貨警示／滿意度大跌：低沉警示音
- 銀行介入／瀕臨破產：心跳聲或警報音
- 達成階段目標：上揚音效

### 5.5 決策面板與歷史時間軸
維持原設計：進貨／定價／排班／行銷四個表單，以及可回看過去數日報表與決策的歷史時間軸，方便玩家覆盤策略。

## 6. 真實世界資料整合方案

### 6.1 關鍵邏輯修正（審查意見：技術架構師，務必注意）

最初構想是「晨報顯示預測天氣，結算時用當天的真實觀測天氣」。**這在邏輯上不成立**：如果遊戲時間可以比真實時間推進得更快（玩家連續按「過一天」），遊戲內的「未來某天」在現實世界根本還沒發生，自然也就沒有「真實觀測值」可以拉取。

**採用方案 A**：遊戲開局時，玩家選擇一個真實城市，系統鎖定一段真實日期區間（如從今天起的可預報範圍）。每個遊戲日的「晨報」顯示**當天的天氣預報值**；結算時，並非去抓「真實觀測值」，而是用「**預報值 ＋ 程式模擬的預報誤差（第 4 節定義的 AR(1) noise）**」來代表現實中「預報有時不準」的體感。文件中所有先前提及「真實結算資料」之處，語意均修正為「預報值＋模擬誤差」。

### 6.2 各資料來源

| 資料類型 | 建議來源 | 備註 |
|---|---|---|
| 天氣 | OpenWeatherMap 免費層 | 提供約 5 天預報，60 次/分鐘、1000 次/天額度；單城市單日快取後實際請求量很低，足以支撐多玩家 |
| 節假日 | Nager.Date 公開 API | 免費、不需金鑰，但**無 SLA 保證**，需加逾時與重試機制 |
| 新聞／社會事件 | RSS／GNews 等來源；NewsAPI 僅在確認免費層授權條款允許商用後才使用 | **僅作晨報頭條的純敘事 flavor 文字**，不直接驅動數值公式，降低授權與雜訊風險 |

### 6.3 快取與容錯
- 同城市同日資料按天快取，TTL 24 小時，並設**最大快取年齡上限**（如 72 小時），避免過期資料被誤當「當日資料」使用
- 外部 API 呼叫一律設短逾時（2～3 秒）＋熔斷降級：逾時或失敗時優先使用最近一次未過期的快取，若無快取則退回預設值（如「晴天」「非節假日」「無新聞頭條」），確保遊戲在外部 API 全部斷線時仍可正常進行（驗收見第 10 節）

## 7. 技術架構建議

### 7.1 整體架構
- **前端**：輕量 SPA（純 JS 或輕框架皆可），以報表／表單渲染為主，無需複雜繪圖
- **後端**：API 服務，負責遊戲狀態管理（開局／推進一天／結算）、外部資料拉取與快取、數值模擬計算

### 7.2 持久化（審查意見：技術架構師）
- MVP 不做完整帳號系統，但**改用 session token（cookie 或 localStorage 內的 UUID）取代「完全無身份」**，避免玩家重整頁面或更換裝置就遺失存檔
- 資料庫：原型階段可用 SQLite，但正式提供多玩家同時遊玩前，需評估遷移至 PostgreSQL，或至少啟用 SQLite 的 WAL 模式並收斂為單一寫入 worker，避免並發寫入鎖表

### 7.3 一致性與冪等性（審查意見：技術架構師）
- 結算 API 加上 **idempotency key（`player_session + game_day`）**並在資料庫加唯一約束，防止玩家連續快速點擊「過一天」造成同一天被重複結算、重複扣款
- 結算當下對外部資料**快照**（複製當下快取內容到本次結算請求），不要在結算過程中即時重讀快取源，避免快取剛好過期更新導致晨報與結算使用到不同版本的資料
- 所有外部 API 呼叫統一包一層 adapter，內建逾時與熔斷邏輯（見 6.3）

### 7.4 資料流程
```
玩家送出決策
   → 後端驗證 idempotency key
   → 讀取／快照當日外部資料快取
   → 執行數值模擬（第 4 節公式 ＋ 第 9 節防異常規則）
   → 寫入結算結果（含唯一約束防重複）
   → 回傳新的一天晨報
```

## 8. 進程與勝負條件

### 8.1 信用評級／銀行耐心值機制（審查意見：遊戲設計師，取代原本單一懸崖式破產線）

原始設計「現金連續 N 天為負即宣告破產」在玩家熟悉數值後會變得可被精算、後期失去張力。改為漸進式財務壓力系統：

| 現金狀態 | 系統反應 |
|---|---|
| 現金 ≥ 0 | 正常經營 |
| 現金 < 0，且銀行耐心值充足 | 銀行介入，按負債金額收取累進利息（負債越多利率越高），玩家信用評級下降一級 |
| 信用評級降至最低且現金仍為負 | 銀行要求抵押庫存／資產折現償債 |
| 抵押後現金仍持續為負，且銀行隨機審查觸發（機率事件，不可預測時機） | 強制清算，遊戲結束 |

隨機審查時機不可預測，保留中後期張力，避免玩家精算出「安全邊際」後就不再緊張。

### 8.2 複合計分（審查意見：遊戲設計師）
最終評分非單純淨資產，採複合制：`最終分數 = 淨資產 × 0.6 + 顧客口碑／忠誠度指數 × 0.4`，避免遊戲收斂成「唯利潤論」、鼓勵玩家兼顧短期獲利與長期口碑經營。

## 9. 數值平衡與防止異常打法（Anti-Exploit 設計）

審查意見（製作人）：防 exploit 機制需要真實對局數據才能精準調參，要求 MVP 文件區分「即時生效、不可妥協的硬規則」與「先有框架、待數據迭代的軟調參」，避免在沒有數據時硬訂死所有係數。

### 9.1 即時生效硬規則（上線即須具備）

| 問題打法 | 防範規則 |
|---|---|
| 天價定價只求成交一筆暴利 | `price_factor` 在 1.5～2.5 倍參考價區間用 `exp(-k×超出比例)` 陡降，**超過 2.5 倍直接強制歸零**，不依賴隨機數兜底；避開「單點硬上限」會被「貼邊反覆試探」的甜蜜點漏洞（見下方說明） |
| 按天雇用臨時工精準卡產能 | 最短任用期 5 天 ＋ 提前解雇資遣費 |
| 大量試價統計反推真實 demand 曲線 | noise 改 AR(1) 時間相關噪聲；UI 不顯示精確 demand／轉換率數字 |
| 長期低價養券、單日狂飆價格大撈一筆 | `ref_price` 改為過去 14 天成交價 EMA，長期低價會拉低 `ref_price`，狂飆時超出比例更大、被重罰更重 |
| 鎖定單一最低彈性品項無限套利 | 跨品項替代需求耦合（見 4.1） |
| 多因子疊加暴衝（節慶+雨天+行銷三重利多同時） | 總疊加倍率整體封頂 ≤3.0（見 4.1） |

> **為何不用「單點硬上限」（如固定 3 倍直接歸零）**：數值平衡審查指出，單點硬上限會在上限前一點（如 2.99 倍）留下無懲罰的「甜蜜點」，玩家會反覆試探貼著上限定價套利。改用「軟性陡降區間（1.5～2.5倍）＋ 超過 2.5 倍才硬歸零」，讓玩家越接近上限、邊際懲罰越重，沒有單一最優貼邊點可鑽。

### 9.2 需數據後迭代軟調參（先建立規則框架，係數待對局數據微調）

| 問題打法 | 框架規則（係數待迭代） |
|---|---|
| 「哄抬物價」後放著被動回血、周期性剝削 | 滿意度恢復**不可純被動回血**，需透過主動促銷／讓利觸發；30 天滾動計次累犯，恢復速度隨累犯次數遞減 |
| 無限加班頂上去就好 | 加班成本 `時數^1.5`（指數待迭代） |
| 無限囤貨躺著賣 | 倉儲超額費用 `(庫存-安全水位)^1.2`（指數待迭代） |

### 9.3 上線驗收要求
上線前需撰寫腳本，以窮舉或簡易強化學習（RL）bot 批次模擬，搜尋各決策維度（定價、囤貨、人力、行銷時機）的理論最優策略，量測其長期（建議 30～60 個遊戲日）期望收益。**驗收標準**：理論最優策略的期望收益不得明顯優於「正常合理經營」基準策略（建議不超過基準的 1.2 倍）。若超標，回頭調整本節係數，此驗收流程併入第 10 節測試計畫。

## 10. 測試計畫／數值驗收 SOP（審查意見：製作人，必交付項）

1. **公式試算表離線驗證**：將第 4、9 節公式建成 Excel／Google Sheet 模型，手動輸入極端參數（如連續 14 天最低價、單日最高價）觀察 `ref_price`、滿意度、現金流是否符合預期、是否仍有未被攔住的暴衝路徑。
2. **腳本批次模擬驗證（對應 9.3）**：寫窮舉/簡易 RL bot，跑數百至數千局模擬，比較「隨機策略」「天真貪婪策略（如固定最高價）」「正常合理經營策略」三者的長期收益分布，確認天真貪婪策略不再是最優解。
3. **內部試玩**：團隊內部至少 3 人各試玩 5～10 局，記錄是否出現「無腦重複操作」（例如每天都做一模一樣的決策也能穩定獲利）的情況，若有則回頭檢視第 4、9 節係數。
4. **外部 API 全斷線降級驗證**：手動模擬天氣／節假日／新聞 API 全部逾時或回傳錯誤，確認遊戲改用預設值（晴天／非節假日／無新聞頭條）後仍可完整跑完一個遊戲日結算流程，不會卡死或報錯。

## 11. 留存與重玩動機（審查意見：製作人，必交付項）

- **起始條件隨機性**：每局可選擇／隨機分配不同真實城市作為商店所在地，不同城市的天氣型態與節慶組合不同，帶來不同的經營節奏與策略重心（如沿海城市颱風事件多、北方城市寒流事件多）
- **難度局**：不同起始資金／起始商店規模解鎖不同難度局，破產或達成目標後可挑戰更高難度
- **複合計分排行**：第 8.2 節的複合分數可作為單機排行榜／歷史最佳紀錄，鼓勵玩家用不同策略風格重玩刷新紀錄
- **NPC 劇情鉤子**（擴充方向，見第 13 節）：固定 NPC 角色的評論台詞可埋入小型敘事支線，作為重玩時的彩蛋與期待感來源

## 12. 建議分階段開發順序

為避免三組外部 API、五類防 exploit 機制、純文字 UX 同時開工導致範圍失控（審查意見：製作人），建議依以下順序分階段實作，**MVP 最終範圍仍涵蓋使用者確認的四件套決策與三類真實資料**，差別僅在開發先後順序：

## 14. 風險與取捨說明

- **天氣／節假日 API**：可靠性高、免費額度足夠 MVP 規模，是核心數值驅動的首選，風險低。
- **新聞類 API**：商用授權條款風險最高（多數免費方案禁止商用），且內容雜訊大、難以穩定轉成數值意義，因此本文件將其定位為**晨報頭條的敘事 flavor**，不作為核心數值驅動來源，待第三階段視效果再評估機制化（第 13 節）。
- **「預報值＋模擬誤差」取代「結算用未來真實觀測資料」**：這是技術架構審查發現的必要邏輯修正——未發生日期的真實觀測值本質上不存在，無法透過任何 API 取得。文件中明確記錄此修正原因，避免讀者誤以為是偷工減料，而是對「真實世界資料如何驅動模擬」這個核心賣點的誠實工程化詮釋。
- **防 exploit 機制的兩層拆分**：硬規則保證上線當下遊戲不會被輕易破壞，軟調參則承認部分係數需要真實對局數據才能精準調校，避免在沒有數據基礎時就假裝所有平衡係數都已經是「最終答案」。
